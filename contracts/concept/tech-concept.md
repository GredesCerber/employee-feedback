# Техническая концепция системы обратной связи сотрудников

Документ описывает реализованный срез MVP на базе `26bf6f1`, включая сохранение данных (#164), лимит запросов (#157) и запуск без Docker (#158), и отдельно план развития. Продуктовая цель — регистрация проблемы или предложения, передача ответственному, прозрачное рассмотрение и видимый автору результат; границы определены [манифестом](../../docs/manifest.md) и [ТЗ](../../docs/tz.md). Новые задачи бэклога не считаются реализованными лишь потому, что запланированы.

## Компоненты

Реализовано: браузерное приложение на React/TypeScript с Vite, клиент HTTP с типами OpenAPI, API на Fastify/TypeScript, изолированное хранилище процесса и синтетический seed. Состав зависимостей и точки сборки: [web/package.json](../../web/package.json), [api/package.json](../../api/package.json), [фабрика API](../../api/src/app.ts), [хранилище](../../api/src/store.ts).

Реализовано: интерфейс выбирает демо-пользователя, отправляет `X-Demo-User` и работает с маршрутами API. Сервер сам определяет роль и подразделение; отказ в доступе нельзя обойти скрытием или показом кнопки. Источники: [HTTP-клиент](../../web/src/api/client.ts), [контекст сессии](../../web/src/app/session.tsx), [проверки API](../../api/src/http.ts).

Реализовано: граница браузер → HTTP API задана [OpenAPI](../api.yaml). Из неё формируются типы клиента и таблица переходов командой генерации; проверка актуальности включена в web-тесты. Источники: [генератор](../../web/scripts/api-types.mjs), [скрипты web](../../web/package.json). План: сохранять этот контракт источником истины и при смене хранилища.

Реализовано: запуск одной командой без Docker — `node infra/run-demo.mjs` из корня репозитория, с Node.js >=22.12.0 и npm. Скрипт устанавливает отсутствующие зависимости по lockfile, собирает API и web, выбирает свободные порты, поднимает локальный веб-сервер с прокси `/api` и печатает адрес браузера; Ctrl+C останавливает оба процесса. Источники: [launcher](../../infra/run-demo.mjs), [локальный сервер](../../infra/serve-demo.mjs), [инструкция запуска](../../infra/README.md). Раздельный запуск через Vite также остаётся доступен: [инструкция API](../../api/README.md), [инструкция web](../../web/README.md). План: отдельно проверять доступность публичного стенда; локальный launcher сам ничего не публикует.

## Модель данных

Реализовано: `Complaint` хранит внутренний ID и номер `A-…`, тип, категорию, подразделение, автора, текст, предлагаемое решение, приоритет, назначение, статус, сроки, комментарии, историю и итоговое решение. `User`, `Category`, `Comment`, `HistoryEvent`, `Decision` и метаданные `Attachment` описаны в [модели API](../../api/src/model.ts) и [схемах контракта](../api.yaml).

Реализовано: запись сначала проверяется, затем сохраняется копией в `Map`; чтение также отдаёт копии. При включённом файловом режиме память обновляется только после успешной записи снимка на диск. Это защищает записи от случайного изменения через результат чтения и частичного изменения при ошибке сохранения, но не является транзакцией базы данных или межпроцессной блокировкой. Источники: [ComplaintStore](../../api/src/store.ts), [файловый снимок](../../api/src/persistence.ts). План: при переходе к базе данных применять транзакции, контроль версии записи и уникальные ограничения.

Реализовано: `PERSIST_FILE` включает сохранение обращений между перезапусками в JSON-файле по абсолютному пути или пути относительно рабочей папки. Снимок проверяется по текущему контракту; запись выполняется атомарно через временный файл рядом со снимком и переименование. Режим рассчитан на один процесс-писатель. Без переменной используется только память и исходный seed; при отсутствии файла создаётся снимок seed. Источники: [FilePersistence](../../api/src/persistence.ts), [подключение в API](../../api/src/app.ts), [инструкция](../../api/README.md), [приёмка сохранения](../../tests/acceptance/92-api-persistence.test.mjs).

Реализовано: новый процесс без файлового снимка получает 20 обращений A-001..A-020; при восстановлении снимка сохраняются его записи, а повторная загрузка seed добавляет только отсутствующие. Статусы, тексты и роли — синтетические; даты ответа для демонстрации аналитики тоже вымышлены. Источники: [seed](../../api/src/seed.ts), [хранилище](../../api/src/store.ts), [данные](../../api/data/seed.json), [исходный датасет](../../docs/dataset.md).

Реализовано: создание и назначение, смена статуса, запрос уточнения, ответ автора и решение формируют историю; завершение требует объяснения, недопустимый переход возвращает 409. Сводка считает категории и типы, долю завершённых, время первой реакции по имеющимся синтетическим датам. Источники: [регистрация и назначение](../../api/src/complaints.ts), [жизненный цикл](../../api/src/lifecycle.ts), [аналитика](../../api/src/analytics.ts).

## Роли и доступ

Реализовано: сотрудник создаёт обращения, видит свои и комментирует свои незавершённые; руководитель видит общую очередь, назначает, меняет статус, запрашивает уточнения и принимает решение; администратор читает записи и сводку. Администратор в этом срезе не управляет обращениями или категориями. Матрица: [концепция доступа](../../api/concept/access.md), нормативные `x-roles` и `x-access-policy`: [контракт](../api.yaml), проверки: [identity и visibleComplaint](../../api/src/http.ts).

Реализовано: неизвестная демо-личность получает 401; запрещённая роль — 403; чужая карточка сотруднику — такой же 404, как отсутствующая. Список ограничивается по автору до фильтров и итогового количества. Руководитель видит все подразделения, а не только своё. Источники: [проверки личности и карточки](../../api/src/http.ts), [список обращений](../../api/src/complaints.ts).

Имитация: `X-Demo-User` и переключатель ролей не обеспечивают защищённую аутентификацию — пользователь может выбрать любую известную демо-личность. Это подходит лишь для синтетического показа; настоящие пользовательские данные так обслуживать нельзя. Источники: [концепция доступа, ограничения](../../api/concept/access.md), [демо-сессия](../../web/src/app/session.tsx).

## Безопасность и персональные данные

Реализовано: тела запросов проверяются по JSON Schema, неизвестные поля и некорректные значения отклоняются; сервер проверяет роли до изменения данных; внешнему клиенту неожиданные ошибки возвращаются без стека. Источники: [валидация и обработка ошибок](../../api/src/http.ts), [приёмка регистрации](../../tests/acceptance/51-api-registration.test.mjs), [приёмка жизненного цикла](../../tests/acceptance/52-api-lifecycle.test.mjs).

Имитация: вложение — только имя, тип и размер файла-заглушки; байты не загружаются. Реализованные ограничения полей описаны в [контракте](../api.yaml). План: реальные вложения принимать только после определения квот, проверки содержимого, прав скачивания, срока хранения и удаления; имя файла не превращать в путь на сервере.

План: до пилота согласовать состав персональных данных, основание обработки, срок хранения, удаление, доступ к журналам и резервным копиям; внедрить настоящую аутентификацию, TLS, секреты вне репозитория, аудит чтения и изменения, резервное копирование с проверкой восстановления. Это проектные требования к пилоту, а не заявление о юридическом соответствии MVP; исходные вопросы зафиксированы в [концепции доступа](../../api/concept/access.md) и [интеграциях](../../docs/research/integrations.md).

Реализовано: POST/PATCH ограничены отдельным окном для каждого известного демо-пользователя — по умолчанию 30 попыток за 60 секунд; неизвестные ID используют общий счётчик. Настройки: `RATE_LIMIT_MAX` и `RATE_LIMIT_WINDOW_S`; `RATE_LIMIT_MAX=0` либо `NODE_ENV=test` отключает ограничение. После исчерпания запрос получает 429 `RATE_LIMITED` и `Retry-After` в секундах без изменения данных; GET не расходует лимит. Источники: [реализация](../../api/src/rate-limit.ts), [приёмка](../../tests/acceptance/90-api-rate-limit.test.mjs), [контракт и общий формат Error](../api.yaml). План: отдельное описание ответа 429 в OpenAPI завершается в #89; фактический лимит уже работает независимо от этой документационной доработки.

План: расширенная анонимность и внешние интеграции ещё требуют отдельной реализации и проверки. Файловое сохранение уже доступно по флагу, но общая БД, миграции и межпроцессная синхронизация остаются планом. Источники текущих границ: [ComplaintStore](../../api/src/store.ts), [FilePersistence](../../api/src/persistence.ts), [концепция доступа](../../api/concept/access.md).

## Интеграции 1С УТ и Битрикс24

План интеграций основан на [исследовании интеграций](../../docs/research/integrations.md); ТЗ не требует реального подключения для MVP. Ниже направления обмена и вопросы перед реализацией, а не подтверждение готовых подключений.

| Планируемый обмен | Направление и минимальные данные | Что уточнить перед пилотом |
|---|---|---|
| План: оргструктура | Битрикс24 → сервис: ID сотрудника, подразделение, руководитель, активность | Источник истины: Битрикс24, AD или 1С ЗУП; допустимые персональные поля; частота обновления |
| План: вход сотрудника | Битрикс24 → сервис: подтверждённый ID и разрешённые роли через согласованную схему входа | Облако или коробка, доступные способы авторизации и требования безопасности |
| План: уведомления | Сервис → Битрикс24: номер, вид события, короткий текст и ссылка; без полного текста обращения | Разрешён ли бот/вебхук, получатели, правила для скрытого автора, повторные попытки |
| План: задачи по решениям | Сервис → Битрикс24: решение, исполнитель, срок, ссылка; обратно → сервис: ID задачи, статус, дата завершения | Кто создаёт задачу, как связывать записи и исключать дубли, что делать при конфликте статусов |
| План: справочники 1С УТ | 1С УТ → сервис, только чтение: код и название номенклатуры, группа; при необходимости номер заказа без условий сделки | Версия конфигурации, допустимость OData/HTTP-сервиса, перечень закрытых полей и прав чтения |

Имитация в текущем приложении ограничена демо-личностями и синтетическими справочниками; отправку в Битрикс24/1С УТ демонстрировать как выполненную нельзя. Источники: [seed](../../api/src/seed.ts), [фактические маршруты](../../api/src/complaints.ts), [описание демо](../../infra/README.md). План: сначала проверять вход и оргструктуру, затем уведомления, потом задачи и только при подтверждённой необходимости справочники 1С УТ.

## Масштабирование

Реализованное хранилище и счётчики лимита принадлежат одному процессу. Файловый снимок переживает перезапуск, но не делает несколько экземпляров API согласованными; запускать несколько писателей с одним `PERSIST_FILE` нельзя. Источники: [ComplaintStore](../../api/src/store.ts), [FilePersistence](../../api/src/persistence.ts), [лимит запросов](../../api/src/rate-limit.ts). План: PostgreSQL с транзакциями и миграциями, общий механизм лимитов, хранение вложений отдельно, серверные сессии или проверенные токены; только после этого — несколько stateless-экземпляров API.

План: обмен с корпоративными системами вынести в очередь событий с повторными попытками, идемпотентным ключом и наблюдаемым состоянием доставки; тяжёлые сводки вычислять по проверенным данным и согласованным определениям метрик. До увеличения нагрузки измерить время ответа и проверить восстановление после отказа, а не считать промышленную готовность из наличия контейнеров. Предмет будущего обмена: [интеграции](../../docs/research/integrations.md); текущие метрики: [аналитика](../../api/src/analytics.ts).

## Ограничения MVP

- Имитация входа вместо SSO; реальные пользователи и оргструктура не подключены. Источники: [сессия](../../web/src/app/session.tsx), [проверка личности](../../api/src/http.ts).
- Без `PERSIST_FILE` данные процесса сбрасываются к seed при перезапуске. С файловым снимком данные сохраняются, но поддерживается только один процесс-писатель; миграции, регулярные резервные копии и межпроцессное согласование остаются планом. Источники: [хранилище](../../api/src/store.ts), [файловый режим](../../api/src/persistence.ts), [инструкция](../../api/README.md).
- Счётчики лимита запросов существуют только в памяти процесса и исчезают после его перезапуска; ограничение не заменяет аутентификацию и распределённую защиту. Источник: [лимит POST/PATCH](../../api/src/rate-limit.ts).
- Основной запуск без Docker работает одной командой; флаг `--seed-reset` в данном срезе передаёт пустой `PERSIST_FILE`, который API отклоняет. До исправления запуск с этим флагом не заявляется рабочим; для исходного seed запускают API без переменной, сохраняя файл отдельно. Источники: [окружение launcher](../../infra/run-demo.mjs), [проверка пути](../../api/src/persistence.ts). План: устранить несовместимость отдельной задачей infra.
- Имитация вложений ограничена метаданными; отправка уведомлений и интеграций остаётся планом. Источники: [контракт Attachment](../api.yaml), [интеграции](../../docs/research/integrations.md).
- Нет анонимной подачи в рассматриваемом срезе; описания будущей анонимности требуют согласования. Источники: [концепция доступа](../../api/concept/access.md), [контракт](../api.yaml).
- Вычисленная сводка показывает работу алгоритма на синтетических датах, а не реальные показатели компании. Источники: [seed](../../api/src/seed.ts), [аналитика](../../api/src/analytics.ts).

## Открытые вопросы

План согласования: [концепция доступа](../../api/concept/access.md) допускает раскрытие анонимного автора администратором в будущем, тогда как новая задача #123 запрещает раскрытие и администратору. До утверждения нового контракта и реализации не считать ни один вариант действующей анонимностью; решение должно определить скрытие имени, ID, автора комментариев и истории во всех ответах.

План согласования: [исследование интеграций](../../docs/research/integrations.md) называет ленту уведомлений и кнопку создания задачи имитацией в MVP, но [фактическое описание демо](../../infra/README.md) отмечает отсутствие уведомлений и обмена. Для этого среза корректно показывать только имеющуюся историю обращения; отдельную ленту или кнопку не заявлять реализованными до соответствующих задач.

План уточнения: [концепция доступа](../../api/concept/access.md) говорит «нет шифрования», а [инструкция запуска](../../infra/README.md) требует HTTPS перед внешней выкладкой. Разделять отсутствие TLS/шифрования в локальном демо и требования к будущей среде; наличие HTTPS на реальном стенде проверять отдельно.

План уточнения: текущая сводка разрешена только администратору по [контракту](../api.yaml), а новые управленческие дашборды предполагают доступ руководителя. До отдельного расширения `x-roles` нельзя расширять права существующего `/summary` по предположению.

## Развитие

План переходов: MVP → пилот → промышленная версия. Объём каждой стадии подтверждается проверяемым результатом, а не обещанием; исходные границы задают [манифест](../../docs/manifest.md) и [ТЗ](../../docs/tz.md).

1. **MVP.** Реализованные сбор и рассмотрение проверяются на синтетическом наборе; имитация входа и вложений явно обозначена. **Критерий перехода:** согласованный сквозной сценарий проходит, роли не обходятся, команда фиксирует ограничения и выбранные метрики. Свидетельства текущей проверки: [E2E-сценарий](../../tests/e2e/demo-path.spec.mjs), [приёмка API](../../tests/acceptance/51-api-registration.test.mjs).
2. **Пилот — план.** Ограниченная группа сотрудников, согласованные правила доступа, настоящая аутентификация, переход от уже реализованного файлового снимка к общей БД PostgreSQL с миграциями, регулярное резервное копирование и один подтверждённый канал уведомления. **Критерий перехода:** владелец процесса принимает результаты измерений, проверено восстановление данных и закрыты вопросы персональных данных и поддержки. Текущий файловый режим: [реализация](../../api/src/persistence.ts); параметры интеграций уточняются по [исследованию](../../docs/research/integrations.md).
3. **Промышленная версия — план.** Подтверждённые требования к нагрузке, доступности, оргструктуре, аудиту, срокам хранения и интеграциям. **Критерий перехода** в регулярную эксплуатацию: согласованы ответственные, процедуры инцидентов, нагрузочные и восстановительные проверки, наблюдаемость и регламент обновлений; после каждого расширения повторяется проверка прав и демо-пути. Основание развития: [ТЗ п. 3.6](../../docs/tz.md).
