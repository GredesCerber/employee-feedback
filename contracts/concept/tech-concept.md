# Техническая концепция системы обратной связи сотрудников

Документ описывает реализованный срез MVP по состоянию main на 12.11.2026: сохранение данных в файле (#164) и в PostgreSQL, лимит запросов (#157), запуск без Docker (#158, #186), анонимная подача (#123), имитация уведомлений и ИИ-подсказки без обязательного ключа; отдельно описан план развития. Продуктовая цель — регистрация проблемы или предложения, передача ответственному, прозрачное рассмотрение и видимый автору результат; границы определены [манифестом](../../docs/manifest.md) и [ТЗ](../../docs/tz.md), краткая схема — в [архитектуре](../../docs/architecture.md). Новые задачи бэклога не считаются реализованными лишь потому, что запланированы.

## Компоненты

Реализовано: браузерное приложение на React/TypeScript с Vite (интерфейс на русском, английском и казахском), клиент HTTP с типами OpenAPI, API на Fastify/TypeScript, хранилище с кэшем в памяти процесса и синтетический seed. Состав зависимостей и точки сборки: [web/package.json](../../web/package.json), [api/package.json](../../api/package.json), [фабрика API](../../api/src/app.ts), [хранилище](../../api/src/store.ts), [словари интерфейса](../../web/src/i18n/messages.ts).

Реализовано: интерфейс выбирает демо-пользователя, отправляет `X-Demo-User` и работает с маршрутами API. Сервер сам определяет роль и подразделение; отказ в доступе нельзя обойти скрытием или показом кнопки. Источники: [HTTP-клиент](../../web/src/api/client.ts), [контекст сессии](../../web/src/app/session.tsx), [проверки API](../../api/src/http.ts).

Реализовано: граница браузер → HTTP API задана [OpenAPI](../api.yaml). Из неё формируются типы клиента и таблица прав и переходов командой генерации; проверка актуальности включена в web-тесты. Источники: [генератор](../../web/scripts/api-types.mjs), [скрипты web](../../web/package.json). План: сохранять этот контракт источником истины и при смене хранилища.

Реализовано: запуск одной командой без Docker — `node infra/run-demo.mjs` из корня репозитория, с Node.js >=22.12.0 и npm. Скрипт устанавливает отсутствующие зависимости по lockfile, собирает API и web, выбирает свободные порты, поднимает локальный веб-сервер с прокси `/api` и печатает адрес браузера; Ctrl+C останавливает оба процесса. `npm run demo:reset` запускает то же на исходном seed без файла данных. Источники: [launcher](../../infra/run-demo.mjs), [окружение потомков](../../infra/demo-env.mjs), [локальный сервер](../../infra/serve-demo.mjs), [инструкция запуска](../../infra/README.md). Раздельный запуск через Vite также остаётся доступен: [инструкция API](../../api/README.md), [инструкция web](../../web/README.md).

Реализовано: выкладка одним сервисом — API сам отдаёт собранный веб из `WEB_ROOT` и хранит данные в PostgreSQL по `DATABASE_URL`; образ и описание сервиса для Render готовы, раздельная выкладка веба и API описана с `CORS_ORIGINS`. Источники: [точка входа API](../../api/src/server.ts), [образ](../../infra/hosted.Dockerfile), [Render](../../infra/render.yaml), [инструкция выкладки](../../infra/deploy/README.md), [CORS](../../api/src/security.ts), [переменные окружения](../../infra/ENV.md). План: доступность публичного стенда проверять отдельно; локальный launcher сам ничего не публикует.

Реализовано: подсказка категории, похожие обращения, дайджест за период и перевод сообщений. Живой вызов модели Anthropic происходит только при заданном `ANTHROPIC_API_KEY`; без ключа подсказка и дайджест строятся по записанным примерам и правилам слов, сеть не используется, перевод отвечает 503 с сохранённым оригиналом. Источники: [провайдер ИИ](../../api/src/ai/provider.ts), [правила](../../api/src/ai/rules.ts), [похожие и подсказка](../../api/src/discovery.ts), [дайджест](../../api/src/digest.ts), [перевод](../../api/src/translations.ts).

## Модель данных

Реализовано: `Complaint` хранит внутренний ID и номер `A-…`, тип, категорию, подразделение, автора, признак анонимности, текст, предлагаемое решение, приоритет, назначение, статус, сроки, комментарии, историю, итоговое решение и необязательную точку на карте. `User`, `Category`, `Comment`, `HistoryEvent`, `Decision`, `GeoPoint`, `AnonymousActor` и метаданные `Attachment` описаны в [модели API](../../api/src/model.ts) и [схемах контракта](../api.yaml).

Реализовано: запись сначала проверяется, затем сохраняется копией в `Map`; чтение также отдаёт копии и всегда идёт из памяти. При файловом режиме память обновляется только после успешной записи снимка на диск. При PostgreSQL изменённые записи отправляются в БД после обновления памяти; неудачная запись остаётся в очереди и повторяется при следующей записи, по таймеру и при остановке. Это не транзакция на уровне запроса и не межпроцессная блокировка. Источники: [ComplaintStore](../../api/src/store.ts), [файловый снимок](../../api/src/persistence.ts), [PostgreSQL](../../api/src/pg-persistence.ts). План: транзакция на каждое изменение, контроль версии записи и уникальные ограничения в реляционной схеме.

Реализовано: `PERSIST_FILE` включает сохранение обращений между перезапусками в JSON-файле по абсолютному пути или пути относительно рабочей папки. Снимок проверяется по текущему контракту; запись выполняется атомарно через временный файл рядом со снимком и переименование. Режим рассчитан на один процесс-писатель. Без переменной используется только память и исходный seed; при отсутствии файла создаётся снимок seed. Источники: [FilePersistence](../../api/src/persistence.ts), [подключение в API](../../api/src/app.ts), [инструкция](../../api/README.md), [приёмка сохранения](../../tests/acceptance/92-api-persistence.test.mjs).

Реализовано: `DATABASE_URL` включает хранение в PostgreSQL (Neon, Render или локальный) и имеет приоритет над `PERSIST_FILE`. Таблица `complaints` создаётся при старте, одно обращение — одна JSONB-строка; сброс демо заменяет все строки в одной транзакции; для нелокальных хостов включается TLS. Источники: [pg-persistence](../../api/src/pg-persistence.ts), [точка входа](../../api/src/server.ts), [переменные](../../infra/ENV.md). План: реляционная схема, миграции и проверка сертификата сервера БД вместо текущего `rejectUnauthorized: false`.

Реализовано: новый процесс без сохранённых данных получает 20 обращений A-001..A-020; при восстановлении снимка или БД сохраняются их записи, а повторная загрузка seed добавляет только отсутствующие. Статусы, тексты и роли — синтетические; даты ответа для демонстрации аналитики тоже вымышлены, `SEED_RELATIVE_DATES=1` сдвигает сроки к текущему дню. Источники: [seed](../../api/src/seed.ts), [хранилище](../../api/src/store.ts), [данные](../../api/data/seed.json), [исходный датасет](../../docs/dataset.md).

Реализовано: создание и назначение, смена статуса, запрос уточнения, ответ автора и решение формируют историю; завершение требует объяснения, недопустимый переход возвращает 409. Руководитель может откатить своё последнее назначение или смену статуса в окне `UNDO_WINDOW_S`. Сводка считает категории и типы, долю завершённых, время первой реакции по имеющимся синтетическим датам; тренды и экспорт CSV доступны руководителю и администратору. Источники: [регистрация и назначение](../../api/src/complaints.ts), [жизненный цикл](../../api/src/lifecycle.ts), [откат](../../api/src/undo.ts), [аналитика](../../api/src/analytics.ts).

## Роли и доступ

Реализовано: сотрудник создаёт обращения, в том числе анонимно, видит свои и комментирует свои незавершённые; руководитель видит общую очередь, назначает, меняет статус, откатывает своё последнее действие, запрашивает уточнения и принимает решение; администратор читает записи и сводку и может сбросить демо-данные. Дайджест, тренды и экспорт доступны руководителю и администратору. Администратор не управляет обращениями или категориями. Матрица: [концепция доступа](../../api/concept/access.md), нормативные `x-roles` и `x-access-policy`: [контракт](../api.yaml), проверки: [identity и visibleComplaint](../../api/src/http.ts).

Реализовано: неизвестная демо-личность получает 401; запрещённая роль — 403; чужая карточка сотруднику — такой же 404, как отсутствующая. Список ограничивается по автору до фильтров и итогового количества. Руководитель видит все подразделения, а не только своё. Источники: [проверки личности и карточки](../../api/src/http.ts), [список обращений](../../api/src/complaints.ts).

Реализовано: анонимная подача — флажок в форме передаёт `anonymous: true`. Настоящий автор хранится для проверки доступа и ответов на уточнения; руководитель и администратор получают `Аноним` без id, роли и подразделения автора, его комментарии и события подписаны «Автор (аноним)»; экспорт и поиск не содержат автора. Это скрытие при показе, а не защита от узнавания по тексту, вложениям или косвенным признакам. Источники: [правило x-anonymity](../api.yaml), [проекция ответов](../../api/src/complaints.ts), [форма подачи](../../web/src/pages/SubmitPage.tsx), [ограничения анонимности](../../api/concept/access.md), [приёмка](../../tests/acceptance/123-anonymous-submission.test.mjs).

Имитация: `X-Demo-User` и переключатель ролей не обеспечивают защищённую аутентификацию — пользователь может выбрать любую известную демо-личность, в том числе автора анонимного обращения. Это подходит лишь для синтетического показа; настоящие пользовательские данные так обслуживать нельзя. Источники: [концепция доступа, ограничения](../../api/concept/access.md), [демо-сессия](../../web/src/app/session.tsx).

## Безопасность и персональные данные

Реализовано: тела запросов проверяются по JSON Schema, неизвестные поля и некорректные значения отклоняются; сервер проверяет роли до изменения данных; внешнему клиенту неожиданные ошибки возвращаются без стека; CORS разрешает только origins из `CORS_ORIGINS`. Источники: [валидация и обработка ошибок](../../api/src/http.ts), [CORS](../../api/src/security.ts), [приёмка регистрации](../../tests/acceptance/51-api-registration.test.mjs), [приёмка жизненного цикла](../../tests/acceptance/52-api-lifecycle.test.mjs).

Имитация: вложение — только имя, тип и размер файла-заглушки; байты не загружаются. Реализованные ограничения полей описаны в [контракте](../api.yaml). План: реальные вложения принимать только после определения квот, проверки содержимого, прав скачивания, срока хранения и удаления; имя файла не превращать в путь на сервере.

План: до пилота согласовать состав персональных данных, основание обработки, срок хранения, удаление, доступ к журналам, БД и резервным копиям (там хранится настоящий автор анонимных обращений); внедрить настоящую аутентификацию, TLS, секреты вне репозитория, аудит чтения и изменения, резервное копирование с проверкой восстановления. Это проектные требования к пилоту, а не заявление о юридическом соответствии MVP; исходные вопросы зафиксированы в [концепции доступа](../../api/concept/access.md) и [интеграциях](../../docs/research/integrations.md).

Реализовано: POST/PATCH ограничены отдельным окном для каждого известного демо-пользователя — по умолчанию 30 попыток за 60 секунд; неизвестные ID используют общий счётчик. Настройки: `RATE_LIMIT_MAX` и `RATE_LIMIT_WINDOW_S`; `RATE_LIMIT_MAX=0` либо `NODE_ENV=test` отключает ограничение. После исчерпания запрос получает 429 `RATE_LIMITED` и `Retry-After` в секундах без изменения данных; GET не расходует лимит. Ответ 429 описан в контракте для операций записи. Источники: [реализация](../../api/src/rate-limit.ts), [приёмка](../../tests/acceptance/90-api-rate-limit.test.mjs), [контракт и общий формат Error](../api.yaml).

Реализовано: уведомления в MVP — лента событий в интерфейсе для сотрудника и руководителя: запрошено уточнение, принято решение, обращение без ответственного, получен ответ автора, близок срок. События строятся из истории обращения, содержат только номер и ссылку, без данных автора, и каждое помечено `simulated: true` с пометкой об имитации email/Битрикс24. Источники: [notifications](../../api/src/notifications.ts), [контракт /notifications](../api.yaml). План: реальная доставка в Битрикс24 по таблице ниже.

## Интеграции 1С УТ и Битрикс24

План интеграций основан на [исследовании интеграций](../../docs/research/integrations.md); ТЗ не требует реального подключения для MVP. В компании используется облачный Битрикс24 ([разбор ТЗ, раздел 8](../../docs/tz-analysis.md)), поэтому подключение планируется через REST API, входящие вебхуки и OAuth-приложение портала, без коробочных модулей. Ниже направления обмена и вопросы перед реализацией, а не подтверждение готовых подключений.

| Планируемый обмен | Направление и минимальные данные | Что уточнить перед пилотом |
|---|---|---|
| План: оргструктура | Битрикс24 → сервис: ID сотрудника, подразделение, руководитель, активность | Источник истины: Битрикс24, AD или 1С ЗУП; допустимые персональные поля; частота обновления |
| План: вход сотрудника | Облачный Битрикс24 → сервис: подтверждённый ID и разрешённые роли через OAuth 2.0 приложения портала | Политика портала для сторонних приложений, требуемые права приложения, требования безопасности |
| План: уведомления | Сервис → Битрикс24: номер, вид события, короткий текст и ссылка; без полного текста обращения. Сейчас — имитация лентой в интерфейсе | Разрешён ли бот/вебхук, получатели, правила для скрытого автора, повторные попытки |
| План: задачи по решениям | Сервис → Битрикс24: решение, исполнитель, срок, ссылка; обратно → сервис: ID задачи, статус, дата завершения | Кто создаёт задачу, как связывать записи и исключать дубли, что делать при конфликте статусов |
| План: справочники 1С УТ | 1С УТ → сервис, только чтение: код и название номенклатуры, группа; при необходимости номер заказа без условий сделки | Версия конфигурации, допустимость OData/HTTP-сервиса, перечень закрытых полей и прав чтения |

Имитация в текущем приложении ограничена демо-личностями, синтетическими справочниками и лентой уведомлений с пометкой «имитация»; отправку в Битрикс24/1С УТ демонстрировать как выполненную нельзя. Источники: [seed](../../api/src/seed.ts), [фактические маршруты](../../api/src/complaints.ts), [уведомления](../../api/src/notifications.ts), [описание демо](../../infra/README.md). План: сначала проверять вход и оргструктуру, затем уведомления, потом задачи и только при подтверждённой необходимости справочники 1С УТ.

## Масштабирование

Реализованное хранилище читает из кэша в памяти одного процесса, а счётчики лимита и стек отката существуют только в этом процессе. PostgreSQL переживает перезапуск, но не делает несколько экземпляров API согласованными: каждый держит свой кэш; запускать несколько писателей с одним `PERSIST_FILE` или одной БД нельзя. Источники: [ComplaintStore](../../api/src/store.ts), [FilePersistence](../../api/src/persistence.ts), [PostgreSQL](../../api/src/pg-persistence.ts), [лимит запросов](../../api/src/rate-limit.ts). План: чтение и запись напрямую в PostgreSQL с транзакциями и миграциями, общий механизм лимитов, хранение вложений отдельно, серверные сессии или проверенные токены; только после этого — несколько stateless-экземпляров API.

План: обмен с корпоративными системами вынести в очередь событий с повторными попытками, идемпотентным ключом и наблюдаемым состоянием доставки; тяжёлые сводки вычислять по проверенным данным и согласованным определениям метрик. До увеличения нагрузки измерить время ответа и проверить восстановление после отказа, а не считать промышленную готовность из наличия контейнеров. Предмет будущего обмена: [интеграции](../../docs/research/integrations.md); текущие метрики: [аналитика](../../api/src/analytics.ts).

## Ограничения MVP

- Имитация входа вместо SSO; реальные пользователи и оргструктура не подключены. Источники: [сессия](../../web/src/app/session.tsx), [проверка личности](../../api/src/http.ts).
- Без `PERSIST_FILE` и `DATABASE_URL` данные процесса сбрасываются к seed при перезапуске. С файловым снимком или PostgreSQL данные сохраняются, но поддерживается только один процесс-писатель; миграции, регулярные резервные копии и межпроцессное согласование остаются планом. Источники: [хранилище](../../api/src/store.ts), [файловый режим](../../api/src/persistence.ts), [PostgreSQL](../../api/src/pg-persistence.ts), [инструкция](../../api/README.md).
- Счётчики лимита запросов и окно отката существуют только в памяти процесса и исчезают после его перезапуска; ограничение не заменяет аутентификацию и распределённую защиту. Источники: [лимит POST/PATCH](../../api/src/rate-limit.ts), [откат](../../api/src/undo.ts).
- Имитация вложений ограничена метаданными; уведомления показываются только лентой в интерфейсе с пометкой «имитация», отправки в email и Битрикс24 нет. Источники: [контракт Attachment](../api.yaml), [уведомления](../../api/src/notifications.ts), [интеграции](../../docs/research/integrations.md).
- Анонимность — скрытие автора при показе, а не его отсутствие: настоящий автор есть в хранилище, а демо-переключатель позволяет войти за автора. Источники: [концепция доступа](../../api/concept/access.md), [контракт](../api.yaml).
- Живой ИИ работает только с ключом Anthropic; без него подсказки и дайджест — правила и записанные примеры, перевод недоступен. Источник: [провайдер ИИ](../../api/src/ai/provider.ts).
- Вычисленная сводка показывает работу алгоритма на синтетических датах, а не реальные показатели компании. Источники: [seed](../../api/src/seed.ts), [аналитика](../../api/src/analytics.ts).

## Открытые вопросы

План согласования: анонимность реализована как скрытие автора, и через API его не получает никто, включая администратора ([концепция доступа](../../api/concept/access.md)). Открыто: кто в компании имеет доступ к БД и резервным копиям, где автор хранится, нужен ли регламент раскрытия при нарушениях и как предупреждать автора о косвенных признаках в тексте и на карте.

План согласования: уведомления сейчас — имитация лентой в интерфейсе ([notifications](../../api/src/notifications.ts)). Для облачного Битрикс24 нужно выбрать канал (бот в чате, системное уведомление или вебхук), получателей и правило для анонимных обращений, чтобы текст уведомления не раскрывал автора ([исследование интеграций](../../docs/research/integrations.md)).

План уточнения: [концепция доступа](../../api/concept/access.md) описывает локальное демо без TLS, а [инструкция запуска](../../infra/README.md) требует HTTPS перед внешней выкладкой. Разделять отсутствие шифрования в локальном демо и требования к будущей среде; наличие HTTPS на реальном стенде и проверку сертификата БД проверять отдельно.

План уточнения: `/summary` по [контракту](../api.yaml) доступен только администратору, а руководитель получает дайджест, тренды и экспорт. Нужно ли руководителю видеть полную сводку и только по своей ветке оргструктуры, решается вместе с подключением оргструктуры, а не расширением `x-roles` по предположению.

## Развитие

План переходов: MVP → пилот → промышленная версия. Объём каждой стадии подтверждается проверяемым результатом, а не обещанием; исходные границы задают [манифест](../../docs/manifest.md) и [ТЗ](../../docs/tz.md).

1. **MVP.** Реализованные сбор и рассмотрение проверяются на синтетическом наборе; имитация входа, вложений и уведомлений явно обозначена. **Критерий перехода:** согласованный сквозной сценарий проходит, роли не обходятся, команда фиксирует ограничения и выбранные метрики. Свидетельства текущей проверки: [E2E-сценарий](../../tests/e2e/demo-path.spec.mjs), [приёмка API](../../tests/acceptance/51-api-registration.test.mjs).
2. **Пилот — план.** Ограниченная группа сотрудников, согласованные правила доступа, вход через OAuth облачного Битрикс24, переход от JSONB-хранения в PostgreSQL к реляционной схеме БД с миграциями, регулярное резервное копирование и один подтверждённый канал уведомления. **Критерий перехода:** владелец процесса принимает результаты измерений, проверено восстановление данных и закрыты вопросы персональных данных и поддержки. Текущее хранение: [PostgreSQL](../../api/src/pg-persistence.ts), [файловый режим](../../api/src/persistence.ts); параметры интеграций уточняются по [исследованию](../../docs/research/integrations.md).
3. **Промышленная версия — план.** Подтверждённые требования к нагрузке, доступности, оргструктуре, аудиту, срокам хранения и интеграциям. **Критерий перехода** в регулярную эксплуатацию: согласованы ответственные, процедуры инцидентов, нагрузочные и восстановительные проверки, наблюдаемость и регламент обновлений; после каждого расширения повторяется проверка прав и демо-пути. Основание развития: [ТЗ п. 3.6](../../docs/tz.md).
