# Полный перечень действий администратора

Сначала перечень, затем воспроизведение сценариев в макете, после согласования
отдельные задачи на реальный продукт. Основание: прямое уточнение капитана
"создавать переименовывать роли нужен ПОЛНЫЙ контроль" от 12 ноября 2026,
#287, #288 и #305. Это основной чек-лист проектирования админ-панели.

**Подтверждено:** управление именами, логинами, состоянием учёток, созданием
и переименованием ролей, правами, сбросом паролей; просмотр глазами пользователя;
синтетические демонстрационные учётки с файлом доступов.
Конкретные механизмы регистрации, сброса, нескольких ролей и хранения аудита
ещё выбираются. В коде текущего MVP этих административных операций нет.

"Полный контроль" означает полный жизненный цикл сущностей и настройку
реализованных разрешений. Название роли не является её идентификатором.
Переименование "Администратор" не должно изменить права или обойти защиту
последнего администратора. Новую роль можно создать без переписывания страниц,
а новый вид разрешённой операции требует серверной реализации и тестов.

## A. Пользователи

| ID | Администратор должен уметь | Проверяемое поведение будущего продукта |
|---|---|---|
| U01 | Просмотреть список, найти и отфильтровать учётки | Поиск по имени/логину, роль и состояние; пагинация и возврат к тому же списку |
| U02 | Открыть карточку | Имя, логин, роль, состояние, несекретные реквизиты; секреты не возвращаются |
| U03 | Создать пользователя | Уникальный логин, проверяемые поля, роль и выбранный способ первичного доступа; понятный следующий шаг |
| U04 | Изменить имя | Новое отображаемое имя видно в карточке и списке, стабильный ID сохраняется |
| U05 | Изменить логин | Сервер проверяет уникальность и согласованную нормализацию; пользователь получает согласованный способ уведомления |
| U06 | Назначить или сменить роль | Видны прежняя и новая роль, последствия для доступа; изменение проверяется сервером |
| U07 | Отключить и включить учётку | Отключённая не входит и не продолжает запрещённые запросы; включение не восстанавливает отозванный одноразовый секрет |
| U08 | Сбросить пароль | Существующий пароль не виден; согласованный одноразовый/временный доступ с ограничением срока и без секрета в аудите |
| U09 | Завершить активные сеансы пользователя | Отозванные сеансы больше не работают; точный механизм и список сеансов описываются в контракте |
| U10 | Увидеть историю административных изменений учётки | Кто, когда, какое несекретное поле изменил, результат и correlation ID |
| U11 | Узнать причину отказа изменения | Дубликат логина, конфликт версии, нет права, отключённая цель, последний администратор различаются понятными сообщениями |
| U12 | Изменить собственные несекретные реквизиты | Обычное редактирование имени/логина не выдаёт дополнительных прав; ограничения собственного доступа явные |

U09 и подробная история сеансов являются предложением завершённого жизненного
цикла, требуют согласования контракта #288. Физическое удаление учёток и истории
не предлагается по умолчанию: сначала отключение/архив, чтобы не потерять авторство
и историю обращений. Если нужно физическое удаление, отдельно определить политику
сохранения данных и анонимизации.

## B. Роли и разрешения

| ID | Администратор должен уметь | Проверяемое поведение будущего продукта |
|---|---|---|
| R01 | Посмотреть все роли | Название, описание, stable ID, встроенная/пользовательская, активная/архивная, число назначенных пользователей |
| R02 | Создать роль | Ввод названия и описания, выбор существующих capabilities; неизвестное право отклоняется сервером |
| R03 | Переименовать роль | Меняется отображаемое имя, stable ID и назначения сохраняются; новое имя появляется у всех назначенных учёток |
| R04 | Изменить описание | Описание не даёт дополнительных прав и не меняет ID |
| R05 | Скопировать роль | Создаётся новый ID с отдельным названием; новая роль не получает встроенные привилегии только от копирования имени |
| R06 | Посмотреть матрицу доступа | Видны разрешения, область данных и объяснение каждого действия |
| R07 | Выдать и отозвать реализованное разрешение | Предпросмотр различий и числа затронутых людей, подтверждение, проверка прав сервера и обновление доступа действующих сессий |
| R08 | Назначить роль пользователям | Выбор разрешённой роли в карточке; список назначений доступен из роли, массовое назначение только отдельной согласованной задачей |
| R09 | Архивировать и восстановить пользовательскую роль | Архивная роль недоступна для новых назначений; для текущих назначений сначала требуется согласованная миграция |
| R10 | Удалить неназначенную пользовательскую роль | Явное подтверждение; назначенную или встроенную роль не удаляем; audit хранит ID и отображаемое имя на момент события |
| R11 | Узнать, почему изменение роли невозможно | Встроенные инварианты, последняя административная учётка, назначения, неизвестная capability, конфликт версии объясняются |
| R12 | Проверить итоговые возможности пользователя | Права и область данных видны без просмотра пароля; отдельно запускается режим только чтения "Глазами пользователя" |

Системную роль можно **переименовать для отображения**, сохранив stable ID,
системное назначение и обязательные ограничения. Нельзя лишить систему последнего
активного административного доступа. Проверка выполняется по серверной модели
прав/системному ID, а не по строке "Администратор". Пользовательские роли полностью
настраиваются в пределах поддерживаемого каталога и разрешённого делегирования.

В первой версии рекомендуется одна роль на учётку. Несколько ролей, deny-правила,
наследование и приоритеты конфликтов нельзя включать молча: сначала выбрать
семантику и протестировать её. Это не отменяет создание и переименование ролей.

## C. "Глазами пользователя"

| ID | Действие | Проверяемое поведение |
|---|---|---|
| V01 | Выбрать цель из списка/карточки | Показываются имя, логин и роль, требуется право на эту цель |
| V02 | Начать просмотр без пароля цели | Сервер создаёт отдельный ограниченный контекст; реальные actor и target различаются |
| V03 | Посмотреть доступные цели экраны и данные | Права администратора не добавляются; анонимность сохраняется; администрационные кэши не видны |
| V04 | Видеть, что включён просмотр | На каждом экране плашка цели и "Только чтение"; изменения и действия с последствиями запрещены на API |
| V05 | Выйти из просмотра | Кнопка всегда доступна, в том числе при ошибке/на телефоне; возврат к исходной карточке, очистка кэша цели |
| V06 | Получить безопасный выход при отзыве/истечении | Отключение цели/actor, отзыв права или истечение контекста закрывают просмотр; потеря исходной сессии ведёт на вход |

Первая версия предполагает просмотр, не действия от чужого имени. Возможность
изменений от имени сотрудника требует отдельного решения. Одно только наличие
admin-прав не должно переписывать события так, будто их совершил сотрудник.

## D. Обзор, обращения и аудит

| ID | Действие | Текущее состояние и проектное решение |
|---|---|---|
| D01 | Посмотреть сводку и динамику | Данные уже есть; объединить в "Обзор" без дублирования и обещаний медианы/персонального мониторинга |
| D02 | Найти и прочитать обращение, историю, итог | API-чтение администратора есть, административный список планируется; право обработки отдельно от права чтения |
| D03 | Найти административное событие | Новый журнал: actor, target, тип действия, время, результат; фильтры без секретов |
| D04 | Проверить изменение роли/пароля/состояния и preview | Журналируются попытка/результат, начало/выход; старый пароль, хэш и одноразовые токены не сохраняются |
| D05 | Понять доступ и ограничения | Матрица и "О прототипе" различают реализованное, имитацию и планы |

Административные полномочия не означают автоматическое снятие анонимности,
возможность переписать историю или бесследно удалить свой аудит. Если нужны
изменяемые категории, маршрутизация, сроки и справочники, это отдельное расширение
предметной области после перечня доступов, а не скрытое добавление к #305.

## E. Подготовка и демонстрация

- Документированный bootstrap первого администратора и восстановление доступа
  при потере секретов без публичного "универсального" пароля.
- Явный демо-режим и воспроизводимый seed; штатные пользователи от него отделены.
- `infra/DEMO-ACCOUNTS.md`: сотрудник, второй сотрудник, руководитель,
  администратор; рабочие синтетические пары, роли и сценарии. В обычном режиме
  эти опубликованные пары не создаются автоматически.
- Проверка прямых API-запросов, а не только видимости меню; 401/403 и маскирование.
- На каждом административном экране: загрузка, пусто, ошибка, частично, нет доступа,
  успех, клавиатура и мобильный возврат. Последний администратор проверяется
  также в параллельных операциях.

## Как переносить перечень в макет и продукт

1. Сверить этот перечень с капитаном и явно отметить выбранные механизмы.
2. В макете воспроизвести ключевой цикл: создать роль → переименовать → изменить
   матрицу → назначить человеку → посмотреть глазами цели → вернуться.
3. Отдельно показать отклонённые операции: занятый логин, последняя админ-учётка,
   удаление назначенной роли, отказ preview. Макет не является реальной защитой.
4. Реализовывать по зонам из [плана](implementation-plan.md), начиная с контрактов
   и независимых тестов. Таблица выше не означает, что всё уже работает в MVP.

Статус покрытия воспроизведённых сценариев записывается в [validation.md](validation.md).
