# Интеграции с 1С УТ и Битрикс24: описание без реализации

> Задача T15 (#17). Основание: ТЗ п. 1.2 и 3.4. **В MVP все интеграции — имитация.** Реальных подключений нет, обмен показываем как события в интерфейсе и синтетические справочники. Так требует манифест (рамка 4) и честная демонстрация (рамка 6).

## И1. Справочник сотрудников и подразделений (Битрикс24)
- **Цель:** не вводить вручную автора, подразделение и ответственного; маршрутизация опирается на актуальную оргструктуру (ТЗ п. 2.5).
- **Состав данных:** ID сотрудника, ФИО, должность, подразделение, руководитель, активен или нет.
- **Направление и способ:** Битрикс24 → система; периодическая выгрузка через REST API (методы пользователей и подразделений) или вебхук.
- **Уточнить:** какая система — источник правды по оргструктуре (Битрикс24, 1С ЗУП или AD); как часто меняется; можно ли хранить ФИО у себя.

## И2. Уведомления (Битрикс24)
- **Цель:** автор и ответственный не пропускают события (ТЗ п. 2.4 «уведомления»; A-011 просит уведомление при задержке).
- **Состав данных:** номер обращения, тип события (назначено, нужно уточнение, решение, просрочено), короткий текст, ссылка на карточку. Текст обращения целиком не передаём.
- **Направление и способ:** система → Битрикс24; входящий вебхук или бот в чате.
- **Уточнить:** допустимы ли уведомления от бота; кому уведомлять об анонимных обращениях, чтобы не раскрыть автора.

## И3. Задачи по принятым предложениям (Битрикс24)
- **Цель:** решение не теряется после «Принято»: у реализации появляются исполнитель и срок, а автор видит прогресс (ТЗ п. 2.7, 1.3).
- **Состав данных:** туда — название, описание решения, исполнитель, срок, ссылка на обращение; обратно — статус задачи и дата закрытия.
- **Направление и способ:** двусторонний; создание задачи через REST, обратный статус через исходящий вебхук.
- **Уточнить:** используются ли задачи Битрикс24 для внутренних улучшений; кто вправе создавать задачи из обращения.

## И4. Вход сотрудника (Битрикс24)
- **Цель:** низкий порог подачи и надёжная привязка обращения к автору (ТЗ п. 2.6).
- **Состав данных:** ID пользователя и роль.
- **Направление и способ:** OAuth 2.0 приложения Битрикс24 или встраивание как приложение портала.
- **Уточнить:** политика безопасности портала для сторонних приложений. Тип портала уже известен: в компании облачный Битрикс24 ([разбор ТЗ, раздел 8](../tz-analysis.md)), поэтому вход — через OAuth-приложение портала.

## И5. Справочники 1С УТ
- **Цель:** аналитика проблем по товарным направлениям и заказам; связь с обращениями вроде A-003 (разные обозначения изделия) и A-007 (повторный ввод).
- **Состав данных:** код и название номенклатуры, товарная группа; при необходимости номер заказа без коммерческих условий.
- **Направление и способ:** 1С → система, только чтение; OData или HTTP-сервис 1С.
- **Уточнить:** версия конфигурации и доступность OData; какие поля нельзя выводить сотрудникам из-за коммерческой тайны (ТЗ п. 3.5).

## Порядок внедрения после MVP
1. И4 и И1 — без них нет реальных пользователей и маршрутизации.
2. И2 — главное средство против потери обращений.
3. И3 — связь решения с исполнением.
4. И5 — только если аналитика по номенклатуре окажется нужна.
