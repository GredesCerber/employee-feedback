# Роли, права, конфиденциальность и анонимность

Опора: [ТЗ п. 2.2, 2.6](../../docs/tz.md), требование R5 в [разборе ТЗ](../../docs/tz-analysis.md), принятый [контракт API](../../contracts/api.yaml) (`x-access-policy`, `x-roles`). Описание совпадает с тем, что реализовано в `api/` (`identity()` и проверки ролей); отличия помечены.

## 1. Роли

| Роль | Кто | Демо-личность |
|---|---|---|
| Сотрудник (`employee`) | Автор обращений | `employee-1`, `employee-2` |
| Руководитель (`manager`) | Рассматривает обращения, назначает ответственных, принимает решения | `manager-1` |
| Администратор (`admin`) | Видит всё и сводку, ничего не меняет в обращениях | `admin-1` |

Роль и подразделение определяет сервер по заголовку `X-Demo-User`, а не по JSON запроса. Это **имитация входа для демо**, а не защищённая аутентификация (подробнее в разделе 5).

## 2. Матрица «действие × роль»

«Свои» значит обращения, где пользователь является автором.

| Действие | Сотрудник | Руководитель | Администратор |
|---|---|---|---|
| Создать обращение | да | нет | нет |
| Видеть обращения (список, карточка, история) | только свои; чужая карточка отвечает 404 | все, включая очередь без ответственного | все |
| Читать справочники (категории, подразделения) | да; список ответственных пустой | да, с ответственными | да, с ответственными |
| Править поля обращения (текст, категорию, тип) | нет | нет | нет |
| Комментировать | да, на своих незавершённых | да | нет |
| Запросить уточнение | нет | да | нет |
| Ответить на уточнение | да, только автор | нет | нет |
| Назначить ответственного | нет | да | нет |
| Сменить статус | нет | да, по допустимым переходам | нет |
| Записать решение или мотивированный отказ | нет | да, объяснение обязательно | нет |
| Читать сводку и аналитику | нет | нет | да |
| Править категории и правила маршрутизации | нет | нет | **развитие**, в MVP справочник только для чтения |

Правила, общие для всех действий:
- Сначала проверяется личность (нет или неизвестна: 401), затем роль (запрещено: 403), затем видимость (чужое обращение для сотрудника: 404, одинаково с несуществующим, чтобы не раскрывать факт его существования).
- Завершённые обращения (реализовано, отклонено, закрыто) неизменяемы: любое изменение даёт 409.
- Каждая ошибка проверяется до записи: данные и история не меняются.

## 3. Что видит каждая сторона

| Сведение | Автор | Ответственный и руководители | Администратор |
|---|---|---|---|
| Текст, предлагаемое решение, вложения-заглушки | да | да | да |
| Статус, следующий шаг, срок, просрочка | да | да | да |
| История событий и комментарии | да | да | да |
| Решение, объяснение и действия | да | да | да |
| Кто назначен ответственным | да | да | да |
| Сводка и повторяющиеся темы | нет | нет | да |

Принцип: автору принадлежит прозрачность хода и результата, руководителям рабочий доступ к обращениям, администратору обзор. Закрытых внутренних заметок в MVP нет, поэтому всё, что пишет руководитель в комментарии или решение, видит автор.

Защита данных в MVP: только синтетические данные (ТЗ п. 3.5), текст хранится как обычный текст и экранируется интерфейсом, тела запросов проверяются по схеме контракта, неизвестные поля отклоняются. В развитие: настоящая аутентификация (SSO через Битрикс24, описание, а не реализация), журнал доступа, срок хранения и удаление по запросу.

## 4. Анонимная подача

В ТЗ анонимность необязательна (п. 2.6). В API MVP реализовано скрытие автора:
сотрудник передаёт `anonymous: true` при подаче. Это конфиденциальность показа,
а не удаление сведений об авторе из хранилища.

**Назначение.** Помогает сообщать о проблемах, о которых сотрудник боится говорить открыто (конфликты, нарушения), и повышает число обращений.

**Как работает.** Система хранит настоящего автора для проверки доступа и ответов.
Сам автор видит свою личность и получает уведомления. Руководители и администратор
видят `author: { name: "Аноним" }`, без id, роли и подразделения в объекте автора.
Его комментарии и действия в истории подписаны «Автор (аноним)». Запросы уточнения,
статусы и решения сохраняют прежний процесс. Публичные представления не меняют
внутреннюю запись; поиск не индексирует имя автора, экспорт не содержит автора.

### Ограничения анонимности
- Полная анонимность без хранения автора несовместима с уточнениями и контролем спама, поэтому выбирается «скрытие автора», а не «отсутствие автора».
- Нельзя гарантировать анонимность по содержанию текста: автор может выдать себя деталями. Это нужно сказать пользователю в форме.
- Вложения, свободный текст и косвенные признаки (подразделение, срок, содержание)
  могут раскрыть автора. Подразделение обращения остаётся видимым для маршрутизации
  и агрегатов. Автоматической очистки текста и вложений от личных сведений нет.
- Администратор через API тоже не получает имя и id автора. Механизма деанонимизации
  нет. Доступ к хранилищу и резервным копиям находится за пределами этой защиты.
- Демо-переключатель роли не является настоящей аутентификацией: пользователь,
  выбравший демо-учётку автора, увидит его собственное представление. Для реального
  внедрения нужны SSO, защита хранилища и контроль доступа к резервным копиям.

**Влияние на процесс.**
- Уточнения: запрос идёт через систему, автор отвечает из своего кабинета, ответственный видит ответ без имени.
- Уведомления: приходят только автору в системе; в письмах и интеграциях нельзя использовать имя автора в теме или тексте.
- Маршрутизация, статусы и сводка не меняются; в сводке анонимные обращения считаются наравне с остальными, но без разбивки по авторам.

**Статус:** API реализован; флажок в форме подачи — отдельная веб-задача #129.

## 5. Ограничения MVP

- Выбор роли через `X-Demo-User` и переключатель в интерфейсе: имитация входа. Скрытие пунктов меню не заменяет проверку на сервере; сервер проверяет права на каждый запрос.
- Хранилище в памяти: данные не переживают перезапуск и не защищены на диске.
- Нет шифрования, ограничения частоты запросов и защиты от перебора идентификаторов (идентификаторы обращений предсказуемы, но доступ ограничен проверкой видимости).
- Нет разграничения по подразделениям: руководитель видит все обращения. В развитие: руководитель видит свою ветку оргструктуры из Битрикс24 (источник и состав данных уточнить).
