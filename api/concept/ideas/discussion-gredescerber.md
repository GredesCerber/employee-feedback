# Обсуждение позиций коллег: взгляд бэкенда

- **Автор:** GredesCerber (капитан, зона `api`)
- **Задача:** #23 (R9)
- **Читал:** [позицию дизайна](../../../design/ideas/ami-m1nzyi-position.md) (Аминат), [позицию фронтенда](../../../web/concept/ideas/punyzxc-position.md) и его идеи (Дамекер), [позицию ресёрча](../../../docs/research/ideas/wohorchik-position.md) (Вадим). Свою позицию см. [gredescerber-position.md](gredescerber-position.md). Критерий сверки: [манифест](../../../docs/manifest.md) и принятый [контракт API](../../../contracts/api.yaml).

## 1. Позиция дизайна (Аминат)

**Согласен.**
- Суть ТЗ и состав R1–R13 с приоритетами совпадают с моими и с [разбором ТЗ](../../../docs/tz-analysis.md) (ТЗ п. 2.3, 2.4, 2.7). Особенно важно требование из R2, что обращение без ответственного остаётся видимым с явным следующим действием: в API это `routing.queue = unassigned` и `nextAction`.
- Просрочка текстом и датой, а не только цветом (R6): API отдаёт `overdue` и `dueAt`.
- Время первого ответа по тестовым датам и явное «нет данных» (R7): в сводке это `averageFirstResponseHours = null`.
- Список «чего быть не должно» совпадает: без реальных данных, без интеграций, без обещаний полной анонимности (ТЗ п. 2.6, 3.5).

**Не согласен или уточняю.**
- *Администратор настраивает категории и маршруты (R5).* В принятом контракте справочник только для чтения, админ видит сводку и ничего не меняет. Для MVP согласен оставить настройку в плане развития, иначе нужны отдельные операции (ТЗ п. 2.2 говорит об этом, но не требует в MVP).
- *Четыре роли (автор, ответственный, руководитель, администратор).* В контракте три: `employee`, `manager`, `admin`; «ответственный» это руководитель, на которого назначено обращение, а не отдельная роль.
- *R8, имитация уведомления «со ссылкой на карточку».* В контракте нет ни ресурса, ни поля для событий уведомлений; имитацию можно строить на фронтенде из `history`, иначе нужна отдельная операция.

## 2. Позиция фронтенда (Дамекер)

**Согласен.**
- Карточка как лента статусов, комментариев и уточнений (R3), блок «Решение» (R4): всё это отдаёт одна операция `getComplaint` с `history`, `comments`, `decision`.
- Переключатель роли с пометкой «имитация» (R5, R12) совпадает с `X-Demo-User`, который контракт прямо называет имитацией входа.
- Без второго трекера или мессенджера, диалоги внутри карточки (ТЗ п. 1.3, 2.5).

**Не согласен или уточняю.**
- *Четыре роли в переключателе:* как выше, в контракте три роли.
- *Единое пространство: «описание (ред. 2, история правок)».* Контракт не разрешает править поля обращения (никакой роли), правки только через комментарии. Либо отказываемся от правок в наброске, либо добавляем операцию и модель версий.
- *Вложения: «прикрепить небольшой файл и увидеть его в карточке», превью и скачивание.* В контракте вложения только метаданные (`isPlaceholder = true`), файл не хранится и не скачивается. Для демо достаточно метаданных, превью и хранение файлов в MVP я бы не делал.
- *ИИ-помощник (демо-режим на записанных ответах в MVP).* Моя позиция [gredescerber-position.md](gredescerber-position.md) не включает ИИ в ядро, а в контракте нет ни одной операции для подсказок. Согласен с условием из его же текста: только на фикстурах, с пометкой «демо ИИ», вне основного пути демо; по правилу отклонения манифеста это идея для развития, пока ядро R1–R4 не готово.

## 3. Позиция ресёрча (Вадим)

**Согласен.**
- Главная боль это потеря обращений и непонятный ответственный (Г1 в [разборе датасета](../../../docs/research/dataset-analysis.md)), поэтому ядро «подал, назначен, решение или мотивированный отказ, автор видит итог» (ТЗ п. 2.3).
- Решение и отказ без текста сохранить нельзя (R4): в контракте `explanation` обязателен и не пустой.
- Реальные интеграции не делаем, только описание (ТЗ п. 1.2, 3.4).

**Не согласен или уточняю.**
- *Анонимность как опция «скрыть имя от ответственного» в MVP (R5).* Контракт и [access.md](access.md) отдают анонимную подачу в развитие: в MVP автор всегда виден.
- *Срок по приоритету в рабочих днях (2 / 5 / 10).* В контракте срок задаёт категория в календарных днях (`dueInDays`).
- *Семь укрупнённых категорий.* Справочник в контракте синтетический и маленький; сами 7 категорий согласен принять, но их нужно внести в seed и в `reference-data`.
- *Подсказка похожих обращений при подаче.* Согласен, что это развитие; в MVP хватает фильтра и поиска `q` по списку.
- *Статус «Закрыто» без зафиксированного результата.* Согласен; в контракте итоговые статусы только через решение с объяснением.

## 4. Спорные вопросы для решения капитана

| № | Вопрос | Варианты | Моя рекомендация | Затрагивает |
|---|---|---|---|---|
| В1 | Сколько ролей в MVP | А. Три (сотрудник, руководитель, администратор), «ответственный» как назначение. Б. Четыре, добавить роль «ответственный» | А: уже в контракте и коде, меньше работы | R5, контракт, дизайн и фронтенд |
| В2 | Анонимная подача в MVP | А. Нет, только описание в развитии. Б. «Скрыть имя от ответственного» на уровне интерфейса и API | А: ТЗ не требует (п. 2.6), нужна отдельная модель доступа и журнал раскрытия | R5, форма подачи |
| В3 | Как считать срок | А. Календарные дни по категории (как в контракте). Б. Рабочие дни по приоритету (2/5/10) | А для MVP; Б можно показать как развитие | R3, R6, seed |
| В4 | Категории | А. Оставить категории из seed. Б. Свести к 7 укрупнённым (Вадим) и обновить seed и справочник | Б, если успеем обновить seed (малая правка); иначе А | R1, R2, форма и сводка |
| В5 | Правка полей обращения и версии | А. Не поддерживаем, только комментарии. Б. Автор может править до рассмотрения, история версий | А | R3, контракт |
| В6 | Вложения | А. Только метаданные файла-заглушки (как сейчас). Б. Загрузка небольших файлов с превью и скачиванием | А для демо; Б в развитие вместе с хранилищем | R1, R11 |
| В7 | ИИ-помощник | А. В развитие. Б. Демо-режим на фикстурах вне основного пути | А пока ядро не готово; Б только если останется время и будет пометка «демо ИИ» | R12, правило отклонения |
| В8 | Уведомления (R8) | А. Лента событий на фронтенде из `history`. Б. Отдельный ресурс уведомлений в API | А: без изменений контракта | R8, фронтенд |
| В9 | Настройка категорий и правил админом | А. Только чтение справочника в MVP. Б. Редактор правил для администратора | А | R5, R2 |

Решения по В1–В9 нужны до того, как кто-то правит контракт или модель данных: изменения затрагивают `contracts/api.yaml`, который меняется отдельной задачей с согласованием обеих зон.
