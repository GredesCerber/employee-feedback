# Позиция бэкенда: суть ТЗ и состав продукта

- **Автор:** GredesCerber (капитан, зона `api`)
- **Тип:** вопрос / позиция для сверки с манифестом

Опора: [ТЗ](../../../docs/tz.md), [датасет](../../../docs/dataset.md), [манифест](../../../docs/manifest.md), [разбор ТЗ](../../../docs/tz-analysis.md). Идеи оформлены отдельными файлами рядом (`gredescerber-<тема>.md`).

## Суть ТЗ в 5 предложениях
1. ГК «Модус Трейд» нужен понятный канал, через который сотрудник сообщает о проблеме или предлагает улучшение (п. 2.1, 2.3).
2. Каждое обращение должно дойти до ответственного по простым правилам, и ни одно не должно потеряться: если ответственного нет, обращение попадает в запасную очередь руководителя (п. 2.5).
3. Ответственный меняет статус, задаёт уточнения и фиксирует решение, включая мотивированный отказ, а автор видит ход и итог (п. 2.3, 2.4).
4. Всё сохраняется, чтобы искать, фильтровать и находить повторяющиеся проблемы, время первого ответа и долю закрытых (п. 2.7).
5. Результат оценивается по бизнес-задаче и честной демонстрации на синтетических данных: что реализовано, что имитация, что план (п. 3.5, 4.2, 4.3).

## Что должно быть в продукте

| Требование | Что делает бэкенд | Приоритет |
|---|---|---|
| R1 подача обращения | Создание обращения с типом, категорией, описанием, предлагаемым решением, метаданными тестовых вложений; номер вида A-0XX; автор берётся из сессии, а не из тела запроса | must |
| R2 маршрутизация | Ответственный по правилу «категория → руководитель»; если правила нет, обращение остаётся в очереди «без ответственного» и видно руководителю | must |
| R3 статусы, сроки, комментарии | Допустимые переходы статусов, срок рассмотрения, комментарии и запрос уточнения с ответом автора, история событий | must |
| R4 решение и отказ | Итог с обязательным объяснением (в том числе отказ), доступный автору | must |
| R5 роли и доступ | Три роли (сотрудник, руководитель, администратор); сотрудник видит только свои обращения (чужое даёт 404); выбор синтетической личности вместо настоящей аутентификации | must (кратко) |
| R6 поиск, фильтры, история | Фильтры по подразделению, категории, статусу, сроку, признак просрочки, история событий карточки | should |
| R7 аналитика | Сводка: число по типам, доля закрытых, среднее время первого ответа, повторяющиеся темы по категориям | should |
| R8 уведомления | Только имитация: запись события «уведомление отправлено» в историю без реальной доставки | should (имитация) |
| R11 техническая концепция | Компоненты, хранение, безопасность, описание (не реализация) интеграций с 1С УТ и Битрикс24 | must (описание) |
| R12 честные ограничения | Таблица «реализовано / имитация / план» в инструкции запуска | must |
| R13 опросы, NPS, клиенты | Не в MVP, только раздел развития | could |

## Чего быть не должно
- Реальных данных компании, клиентов, сделок и сотрудников: только синтетика (ТЗ п. 3.5).
- Реальных интеграций с 1С УТ и Битрикс24 в MVP: максимум описание цели, состава и направления данных (п. 1.2, 3.4).
- Настоящей аутентификации и хранения паролей: демо-идентификация названа имитацией и не выдаётся за промышленную защиту.
- Реальной загрузки файлов: только метаданные файлов-заглушек.
- Клиентской обратной связи, опросов и NPS в ядре MVP (п. 2.2).
- Функций без связи с пунктом ТЗ и без возможности показать на демо (правило отклонения из манифеста).
- Утверждений о промышленной готовности: мы показываем MVP и честно называем ограничения.
