# Идея: Единое рабочее пространство вокруг обращения

- **Автор:** punyzxc
- **Тип:** функция / вариант интерфейса

## Проблема
Обсуждение предложения сейчас расползается по почте, чатам и задачам, и автор не видит, что с ним стало (ТЗ п. 1.3: «сокращение потерь обращений», «прозрачность рассмотрения»). Датасет прямо об этом: A-010 просит держать связанные вопросы «в общей истории обсуждения», A-015 о поручениях без результата и срока.

## Идея
Одно приложение для всех сотрудников «Модус Трейд», в котором у каждого обращения есть живая карточка: прогресс по этапам (новое → на рассмотрении → в работе → решено), диалог автора с ответственным, вопросы и уточнения, правки описания с историей версий и вложения (документы, графика). Главная страница сотрудника показывает «мои обращения» с прогрессом, у ответственного очередь, у руководителя сводка. Действия по решению (например, «подготовить шаблон заявки» из A-001) можно оформить как подзадачи с ответственным и сроком внутри карточки.

Набросок карточки:
```
A-001 · Проблема · Межотдельное взаимодействие          [В работе ▸ 3/4]
Ответственный: Руководитель закупок · срок 14.11 · осталось 2 дня
─ Лента ───────────────────────────────────────────────
 Автор: описание (ред. 2, история правок)  📎 пример-заявки.pdf
 Ответственный: ❓ Пришлите пример корректной заявки
 Автор: ответ + 📎 заявка-образец.xlsx
 Статус → В работе
─ Действия ────────────────────────────────────────────
 ☐ Оценить изменение шаблона — Руководитель закупок, до 20.11
```

## Проверка по манифесту
- Связь с ТЗ (пункт): 2.3 (шаги 2-5), 2.4 (комментарии, уточнения, статусы, история), 2.5, 2.7; R1, R3, R4, R10.
- Можно показать на синтетических данных: да, на A-001, A-010, A-015.
- В MVP или в развитие, почему: **в MVP в урезанном виде**: карточка-лента, диалог и уточнения, история правок описания, вложения. **В развитие**: подзадачи с ответственными и сроками и использование приложения как общего трекера задач компании.

## Риски и допущения
- **Расхождение с ТЗ.** Общий трекер «всех задач всех сотрудников» и мессенджер выходят за рамки ТЗ (это система обращений, не управление проектами) и пересекаются с Битрикс24, который в компании уже есть (п. 1.2). Поэтому в MVP прогресс и диалоги только вокруг обращений; связь с задачами Битрикс24 описываем как интеграцию (п. 3.4).
- Правка описания после подачи должна сохранять историю, иначе теряется прозрачность решения.
- Решение о границе MVP за капитаном (T19).
