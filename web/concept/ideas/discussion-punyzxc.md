# Обсуждение позиций коллег: взгляд фронтенда

- **Автор:** punyzxc (Дамекер, зона `web`)
- **Задача:** T22 (#22)
- **Прочитано:** [дизайн, Ami-m1nzyi](../../../design/ideas/ami-m1nzyi-position.md), [бэкенд, GredesCerber](../../../api/concept/ideas/gredescerber-position.md), [ресёрч, Wohorchik](../../../docs/research/ideas/wohorchik-position.md). Моя позиция: [punyzxc-position.md](punyzxc-position.md).
- **Сверено с тем, что уже в main:** контракт [`contracts/api.yaml`](../../../contracts/api.yaml), модель доступа [`api/concept/access.md`](../../../api/concept/access.md), seed `api/data/seed.json`, экраны `web/src/pages/`.

## 1. Дизайн (Ami-m1nzyi)

**Согласен:**
- Ядро R1–R4 и R10 как маршрут «подача → назначение → уточнение → ответ автора → решение → просмотр итога» (ТЗ п. 2.3). Это ровно наш демо-путь, и экраны `/submit`, `/my/:id`, `/queue/:id` его уже закрывают.
- Просрочка текстом и датой, а не только цветом (R6, ТЗ п. 2.4): это важно для доступности и для проектора на защите.
- Обращение без ответственного видно в очереди руководителя с явным следующим действием (R2, ТЗ п. 2.5). В контракте есть категория `no_rule_demo` и `queue=unassigned`.
- В макете явно показывать, кто что видит и меняет (R5, ТЗ п. 2.6).
- R8 как имитация уведомления со ссылкой на карточку.

**Не согласен или уточняю:**
- В R5 у дизайна администратор «настраивает категории и маршруты». В контракте и `access.md` справочник в MVP только для чтения, правка правил в развитии. Экран настройки нарисовать можно, но работать он не будет, и его надо помечать «План» (R12). См. вопрос В5.
- Дизайн не говорит, как фронтенд показывает имитацию. Сейчас в `web/src` нет ни одной пометки «имитация», а R12 must (ТЗ п. 4.2). Нужен единый бейдж (предложено в фидбеке #82).

## 2. Бэкенд (GredesCerber)

**Согласен:**
- Автор берётся из сессии, а не из тела запроса; сотрудник видит только свои (чужое 404); права проверяет сервер на каждый запрос (R5, ТЗ п. 2.6). Фронтенд скрывает пункты меню только для удобства, не для защиты.
- Реальной загрузки файлов нет, только метаданные заглушки (ТЗ п. 3.5). Это совпадает с моей идеей о вложениях: большие архивы и объектное хранилище в план.
- Таблица «реализовано / имитация / план» в инструкции запуска (R12). Уже сделана в `infra/README.md` (#58, ждёт сдачи).
- Интеграции с 1С УТ и Битрикс24 только описанием (R11, ТЗ п. 1.2, 3.4).

**Не согласен или уточняю:**
- R8 у бэкенда: «запись события "уведомление отправлено" в историю». В контракте сейчас уведомлений нет вообще (описание контракта: «No ... notifications»), а в интерфейсе их не видно. Запись только в историю жюри не заметит: ТЗ п. 2.5 прямо спрашивает, «каким образом автор узнаёт о ходе работы». Предлагаю показывать во фронтенде ленту событий из уже существующей истории без нового API (фидбек #81). См. вопрос В3.

## 3. Ресёрч (Wohorchik)

**Согласен:**
- Главная боль по датасету: непрозрачный статус и ответственный (группа Г1). Поэтому карточка автора с ответственным, сроком и следующим шагом главный экран (ТЗ п. 1.3, 2.3).
- Решение и отказ без текста не сохраняются (R4); в контракте и в `ComplaintActions.tsx` это уже так.
- R8 как лента событий в интерфейсе: совпадает с моим предложением (#81).
- Подсказка похожих обращений при подаче в развитии: совпадает с моей идеей про ИИ-помощника (`punyzxc-ai-assistant.md`), её демо-вариант без внешнего API предложен в #83.

**Не согласен или уточняю:**
- **Четыре роли** (автор, ответственный, руководитель направления, администратор). В контракте и `access.md` три: `employee`, `manager`, `admin`; ответственный и руководитель совмещены в `manager`. Четвёртая роль меняет контракт, права и экраны за сутки до сдачи. См. В1.
- **Анонимность в MVP** как опция «скрыть имя». Контракт прямо запрещает анонимные обращения, `access.md` относит её к развитию. Это противоречие уже отмечено в ревью PR #79. См. В2.
- **7 укрупнённых категорий вместо 18 из датасета.** Seed сейчас создаёт категории из датасета как есть (плюс `no_rule_demo`). Укрупнение полезно для сводки (R7), но меняет seed, маршрутизацию и фильтры. См. В4.
- **Срок по приоритету.** Сейчас у всех категорий `dueInDays: 7`. Срок по приоритету делает просрочку на демо реалистичнее (R6), но это правка seed и API. См. В4.

## 4. Где все сходятся

- Синтетические данные, никаких реальных интеграций, опросы и NPS только в развитии (R13, ТЗ п. 2.2, 3.5).
- Обращение не теряется: запасная очередь без ответственного (R2).
- Отказ всегда с объяснением, автор видит итог (R4).
- Честная демонстрация «реализовано / имитация / план» (R12).

## 5. Вопросы для решения капитана

Каждый спор сведён к вопросу с вариантами. Рекомендация фронтенда отмечена ★.

**В1. Сколько ролей в MVP?** (R5, ТЗ п. 2.2, 2.6)
- А ★ Три роли контракта (`employee`, `manager`, `admin`), «ответственный» = руководитель категории. Ничего не меняем.
- Б Четыре роли, как у ресёрча: отдельный «ответственный». Нужна правка контракта, прав, seed и экранов очереди.

**В2. Анонимная подача?** (R5, ТЗ п. 2.6)
- А ★ Не в MVP: описание в `access.md`, в демо помечаем «План».
- Б Галочка «скрыть имя» в форме только визуально, сервер по-прежнему хранит автора. Риск: выглядит как функция, которой нет.
- В Полноценно: правка контракта, прав и карточки. Риск по срокам.

**В3. Как показываем уведомления (R8)?** (ТЗ п. 2.4, 2.5)
- А Только запись в историю карточки (позиция бэкенда).
- Б ★ Колокольчик и лента событий во фронтенде из существующей истории, без нового API, с бейджем «Имитация» (#81).
- В Не показываем, только в слайдах.

**В4. Категории и сроки для демо.** (R2, R6, R7)
- А ★ Оставить категории датасета и `dueInDays: 7`; для просрочки подобрать синтетические даты в seed. Укрупнение и срок по приоритету в план.
- Б Ввести 7 укрупнённых категорий и срок по приоритету сейчас (правка seed, API и фильтров).

**В5. Экран администратора «категории и маршруты».** (R5, R11)
- А ★ Только просмотр справочника с бейджем «Правка правил: план».
- Б Не показывать на демо, описать в техконцепции.
- В Сделать редактирование. Нужен новый API, вне контракта.

**В6. Демо-ИИ в форме подачи.** (идея T8, R1, R7)
- А Не делаем, только в плане развития.
- Б ★ Демо-режим без сети: похожие обращения по совпадению слов и категория по записанному ответу, бейдж «Демо ИИ» (#83). Делаем, только если ядро и #81/#82 готовы.
- В Живой внешний API. Не рекомендую: безопасность данных (ТЗ п. 3.5), ключи, доступность из РФ.
