# Подход к интерактивному прототипу и структуре фронтенда

- **Автор:** punyzxc (зона `web`)
- **Задача:** T10 · требования R10, R12
- **Статус:** предложение. Окончательный стек выбирает задача T32 (`api/concept/stack-decision.md`), границу MVP задача T19. Если T32 выберет «только кликабельный прототип», структура ниже остаётся, меняется только источник данных (см. «Запасной вариант»).

## Цель прототипа

Провести жюри по сценарию демо из PRD за 3 минуты: подача (R1) → автоназначение (R2) → статусы и уточнение (R3) → решение и мотивированный отказ (R4) → фильтры и просроченные (R6) → сводка и повторы (R7). Каждый экран честно показывает, что работает по-настоящему, а что имитируется (R12).

## Библиотеки

Опираемся на стек репозитория `web-node` (`hk.config.json → scaffold`): `npm create vite@latest web -- --template react-ts`.

| Что | Библиотека | Почему |
|---|---|---|
| Сборка и dev-сервер | Vite + React 18 + TypeScript | уже в каркасе, быстрый старт, проверки `web-types` в `hk check` |
| Маршруты экранов | React Router | у каждого экрана свой адрес, по ссылке из «уведомления» открывается карточка (R8) |
| Данные с API | TanStack Query | кеш, загрузка, ошибки и повтор без своей обвязки |
| Формы и проверка | React Hook Form + Zod | те же схемы Zod, что в `api` (Fastify + zod), меньше расхождений с контрактом |
| Таблицы, фильтры | TanStack Table | фильтры по подразделению, категории, статусу, сроку (R6) |
| Графики сводки | Recharts | 2-3 простых графика для R7 |
| Стили | CSS-переменные из `web/src/styles/` (зона design) | дизайн-токены задаёт дизайн, фронтенд не изобретает свои |
| Тесты | Vitest + Testing Library; Playwright для демо-пути (`tests/e2e/`) | `web-test` в `hk check`, E2E «счастливого пути» по AGENTS.md |
| Имитация API без бэкенда | MSW (Mock Service Worker) | запасной вариант, если API не успеет; те же запросы, что к настоящему API |

Новых тяжёлых UI-китов не берём: экраны простые, время дорого.

## Структура `web/`

```
web/
  src/
    app/            маршруты, провайдеры (Query, роль демо)
    pages/          по экрану на шаг демо
      submit/         1. форма подачи (R1)
      my/             «Мои обращения» автора (R3, R4)
      appeal/         карточка-лента: статусы, уточнения, решение (R2-R4)
      queue/          очередь ответственного/руководителя, фильтры, просрочка (R2, R6)
      summary/        сводка и повторы (R7)
      admin/          категории и правила маршрутизации (R5), только просмотр в MVP
    features/       куски экранов: role-switcher, status-badge, clarify-form, decision-block, demo-notice
    api/            клиент по contracts/ (типы генерируются из OpenAPI, вручную не пишем)
    mocks/          MSW-обработчики и фикстуры из docs/dataset.md (A-001 … A-020)
    styles/         токены дизайна (зона design)
  concept/          тексты, макеты, идеи (первый день)
```

Правила:
- Типы запросов только из `contracts/` (источник правды по AGENTS.md); фронтенд под контракт, не наоборот.
- **Переключатель роли** в шапке (автор / ответственный / руководитель / админ): на одних данных показывает разницу прав (R5). Это демо-приём, а не вход в систему.
- **Метка «Имитация»** (`demo-notice`) на каждом элементе, за которым нет настоящей логики (уведомления, интеграции, ИИ).

## Что настоящее, что имитация, что план (R12)

| Функция | Шаг демо | Реализовано | Имитация | План развития |
|---|---|---|---|---|
| Форма подачи: тип, категория, описание, предполагаемое решение | 1 | ✓ сохраняется через API, выдаётся номер | | |
| Вложение к обращению | 1 | ✓ небольшой файл-заглушка | | большие архивы, загрузка по частям, объектное хранилище |
| Назначение ответственного по категории, запасной путь «без ответственного» | 2 | ✓ простые правила из таблицы категорий | | гибкие правила, замещение, загрузка из оргструктуры |
| Статусы, сроки, история, запрос и ответ на уточнение | 3 | ✓ | | |
| Решение и мотивированный отказ, видимые автору | 4 | ✓ | | |
| Поиск по номеру, фильтры, просроченные | 5 | ✓ | | сохранённые фильтры |
| Сводка: типы, доля закрытых, время первого ответа, повторы | 6 | ✓ по тестовым датам | повторы по совпадению категории и ключевых слов | семантический поиск дублей |
| Роли и права | все | ✓ проверка роли на API | вход: переключатель роли вместо логина | SSO / учётки Битрикс24 |
| Уведомления автору и ответственным | 3, 4 | | ✓ список событий и значок внутри приложения | email, Битрикс24 |
| ИИ-помощник (подсказка категории, черновик ответа) | 1, 4 | | ✓ записанные ответы модели на обращения датасета, метка «демо ИИ» | живой API после решения по безопасности данных (ТЗ п. 3.5) |
| Интеграция с 1С УТ и Битрикс24 | — | | | описание в техконцепции (R11), реализация после уточнений |
| Опросы, NPS, клиентская обратная связь | — | | | R13, после проверки внутреннего процесса |

Строки «ИИ-помощник» и «Вложения» зависят от решения капитана по идеям T8 (`web/concept/ideas/punyzxc-*.md`); если их не берут в MVP, они переезжают в колонку «План».

## Данные для демо

Только синтетика (манифест, п. 3): 20 обращений из `docs/dataset.md` загружаются как начальные данные. Для R2 и R12 добавляем отдельные выдуманные примеры: обращение с категорией без ответственного и обращение с мотивированным отказом (A-017). Даты подбираем так, чтобы были просроченные (A-011) и считалось время первого ответа.

## Запасной вариант

Если бэкенд не готов к демо, фронтенд переключается на MSW (`VITE_USE_MOCKS=true`): те же экраны и запросы, ответы из `web/src/mocks/`. В таком режиме в шапке горит метка «Демо-данные, сервер не подключён», чтобы не выдавать имитацию за работающую систему (R12).

## Открытые вопросы к капитану

1. Берём ли ИИ-помощник в MVP в демо-режиме или только в план (идея `punyzxc-ai-assistant.md`)?
2. Нужен ли экран администратора в демо или достаточно упоминания в техконцепции?
3. Подтверждает ли T32 стек `web-node` (Fastify + zod), чтобы делить схемы Zod между `web` и `api`?
