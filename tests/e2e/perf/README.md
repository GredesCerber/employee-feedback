# Нагрузочный smoke API

Из корня репозитория после установки зависимостей и сборки API:

```text
npm --prefix api ci
npm --prefix api run build
node tests/e2e/perf/smoke.mjs
```

Скрипт использует только Node.js и установленный API проекта. Docker, внешние утилиты и сетевые сервисы не нужны. Он запускает отдельный `buildApp()` на свободном порту `127.0.0.1`, одновременно отправляет 200 запросов: 67 GET списка, 67 GET карточки A-001, 66 POST подачи. Измеряется время от отправки до полного чтения тела ответа; создание сервера и сборка в него не входят. В конце сервер закрывается.

Перед созданием приложения скрипт выставляет `RATE_LIMIT_MAX=0`, выводит уведомление и использует отдельное хранилище в памяти (`PERSIST_FILE=''`). Прежние значения восстанавливаются после прогона, в том числе при ошибке. Рабочий демо-сервер и его данные не затрагиваются.

Первая таблица показывает число ответов каждого HTTP-кода. Вторая — количество запросов и p50/p95/max в миллисекундах. Процентили рассчитаны методом nearest rank: p95 — 190-е время в отсортированном наборе из 200. Код выхода 0 означает успешные HTTP-ответы и p95 не выше порога. Код 1 означает превышение порога, 5xx, другой неуспешный HTTP-код, сетевую ошибку или ошибку запуска; причина печатается после `FAIL`. Запросы ограничены 15 секундами.

Порог по умолчанию — **300 мс**. Его можно изменить переменной `PERF_P95_MS`; значение должно быть положительным числом. В PowerShell:

```powershell
$env:PERF_P95_MS='500'
node tests/e2e/perf/smoke.mjs
Remove-Item Env:PERF_P95_MS
```

В macOS/Linux:

```sh
PERF_P95_MS=500 node tests/e2e/perf/smoke.mjs
```

Сам скрипт не запускает shell и не зависит от синтаксиса командной оболочки. Для сравнения запусков используйте один порог и сходную загрузку машины. Увеличенный порог меняет критерий прогона и не означает прохождение исходных 300 мс.

Проверки самого инструмента (процентили, пороги, параллельность, отключение лимита, закрытие сервера при ошибках) запускаются отдельно:

```text
node --test tests/e2e/perf/smoke.test.mjs
```

Эти unit-тесты лежат в разрешённой папке задачи; текущая общая команда `hk check` автоматически запускает только `tests/acceptance/`, поэтому при изменении инструмента выполняйте обе проверки.
